01

Authentication

FIXED — was 1 critical

Login, logout, registration, password reset, and the two-step email-OTP flow were tested end to end, including deliberately breaking each one.

Blank Date of Birth on registration crashes the site and permanently kills the email addressCritical
Steps
POST to /register/ with date_of_birth omitted (any API client, or a browser dev-tools edit — the HTML form's own required attribute is the only thing stopping a normal user).
Expected
A validation error; no account created.
Actual
Django's full debug 500 traceback page (source paths, settings) is returned, and the User row is already committed before the crash. That email is now permanently unusable — no Patient profile exists to log in with, and the app has no delete-account feature.live-reproduced & cleaned up
Fix
Add date_of_birth to register()'s existing required-field guard, and wrap the User + Patient creation in transaction.atomic() so a downstream failure can't leave an orphaned account.
All 4 "change password" forms crash on a blank new passwordHigh
Steps
Authenticated, POST the correct current_password but omit new_password/confirm_new_password.
Expected
"Please fill in all fields" style error.
Actual
Only an equality check exists (new == confirm), which two Nones pass. validate_password(None, user) then throws an uncaught TypeError — 500.
Fix
Add the same blank-check reset_password_confirm already has, to patient/doctor/receptionist/adminpanel's change_password.
Duplicate-email race on registration/onboarding has no DB-level fallbackMedium
Steps
Two near-simultaneous signups with the same email (self-register, walk-in registration, or admin onboarding).
Expected
Second one is rejected cleanly.
Actual
Both check .exists() before creating; the loser hits the DB unique constraint directly and gets an uncaught IntegrityError instead of a friendly message.
Fix
Wrap the four create_user() call sites in try/except IntegrityError.
Login, OTP lifecycle, and lockout all work correctly end to endPass
Verified
Wrong password / non-existent email both return the same generic "Invalid email or password" (no account enumeration). With OTP switched on: attempts-remaining counter decrements correctly (3→2→1), 3rd wrong code wipes the OTP, sets a real 10-minute otp_locked_until, and shows "Too many incorrect attempts. Your account is locked for 10 minutes." on return to /login/ — confirmed via a clean curl session after the in-browser check first (misleadingly) appeared to drop the message. Correct-code path logs in and redirects to the right role dashboard. Logout calls real django.contrib.auth.logout().
Logged-in users can still open /login/ and /register/Low
Actual
No redirect-if-authenticated guard. No security impact (register creates a separate account, doesn't touch the current session) — just a small UX inconsistency.
Fix
Redirect to the role dashboard if request.user.is_authenticated.
02

Role-Based Access

FIXED — was 1 medium gap

Every view across all 5 apps was checked for its decorator, then cross-checked live by logging in as each role and hitting other roles' URLs directly.

No patient_required decorator — patient views rely on convention, not enforcementMedium
Steps
Log in as a doctor, receptionist, or admin; visit /patient-profile/ or /book-appointment/.
Expected
Redirected away — patient-only area.
Actual
Fully accessible. Patient.objects.get_or_create(user=request.user) silently creates a Patient record for a doctor/receptionist/admin account, and they can then book and pay for their own appointment under it. This isn't hypothetical: the seeded admin account "Vikrant Mehta" has real appointments and bills against it right now, live-confirmed on the admin dashboard.
Fix
Add a patient_required decorator mirroring doctor_required/receptionist_required/admin_required (all three of which are correctly implemented — see Pass below), and apply it to all 14 patient-app views.
Doctor / Receptionist / Admin decorator coverage is complete and correctPass
Verified
15/15 doctor views, 21/21 receptionist views, 22/22 admin views carry a role decorator that checks request.user.role (not just is_authenticated). Live-tested: the account-deactivation privilege-escalation guard correctly refused to deactivate the admin account itself ("Administrator accounts cannot be deactivated from here."), and toggling a doctor's active status worked and round-tripped cleanly.
Note
Django's own /admin/ site is a separate privilege plane gated by is_staff (never set by the app's own signup flows) rather than the app's role field — low real-world risk today, but architecturally worth reconciling.

Patient Module

FIXED — was 1 critical

Profile, appointment booking, medical records/prescriptions, and billing — tested as seeded patient Anita Sharma.

Patients can book — and pay for — an appointment dated in the pastCritical
Steps
On the booking form, submit appointment_date=2020-01-15 for any doctor/slot (bypasses only a client-side JS min, e.g. via dev tools or a direct POST).
Expected
Rejected — dates before today aren't bookable.
Actual
Booking sailed through to the real confirm-and-pay screen showing "Date: Jan 15, 2020 · Consultation with Dr. Arjun Rao · ₹1000 Total Due" — one click from creating a fully paid, backdated appointment + bill. Root cause: Doctor.get_available_slots() only special-cases today (skipping already-elapsed same-day slots); it never rejects a date that's entirely in the past, and neither booking view adds its own date.today() check.live-reproduced to the payment screen, then cancelled
Fix
Add if parsed_date < date.today(): reject — ideally inside get_available_slots() itself so every caller (patient and receptionist booking) inherits the fix in one place.
Profile name field accepts raw script tags — but is safely escaped everywhere it's shownLow
Steps
Set First Name to <script>alert('xss')</script> and save.
Actual
Saved verbatim, but Django's template auto-escaping correctly neutralizes it everywhere (navbar greeting, profile heading) — confirmed via DOM inspection, no script execution. Not a security bug, but the field has zero format validation.live-tested, reverted
Fix
Cosmetic: restrict name fields to letters/spaces/hyphens for data hygiene, not security.
Cross-patient data access (IDOR) is correctly blocked everywhere checkedPass
Verified
Requesting another patient's billing receipt (/my-billing/31/receipt/, a real bill belonging to a different account) returns a clean 404, not the data. Same ownership-scoped pattern confirmed by reading cancel_appointment, dismiss_notification, my_appointments, my_billing.
Patient-facing pages silently drop error messagesMedium
Steps
Submit the Contact form with every field blank.
Expected
"Please fill in all required fields" shown on the page.
Actual
templates/patient/base.html has no {% if messages %} block at all, and contact.html doesn't add its own — the message is genuinely queued server-side (it surfaced on the next page that does render messages) but never shown to the visitor who submitted the form.live-confirmed via direct POST
Fix
Add a shared messages block to patient/base.html (same fix needed once, not per-page).

Doctor Module

FIXED — was 1 high

Dashboard, availability, prescriptions, patient records — tested as Dr. Sarah Mitchell.

Availability form accepts an inverted time range with zero feedbackHigh
Steps
Set Monday's hours to Start 17:00, End 09:00, Save.
Expected
Rejected, or auto-corrected with a warning.
Actual
Saved silently, no error. Confirmed in the database: start_time=17:00, end_time=09:00. Downstream, get_available_slots() then produces zero bookable slots that day — the doctor is effectively invisible on Mondays with no indication why.live-reproduced, reverted
Fix
Reject (or clearly flag) end_time <= start_time server-side, mirrored client-side for instant feedback.
Negative consultation fee crashes the profile save with a raw DB errorMedium
Steps
Edit profile, set Consultation Fee to -500, submit.
Expected
"Fee must be positive" validation error.
Actual
Uncaught django.db.utils.DataError: Out of range value for column 'consultation_fee' (500) — the field is an unsigned MySQL column with only a bypassable client-side min="0" guarding it. No data corruption (the failed save doesn't partially apply), but a hard crash.live-reproduced via test client
Fix
Validate consultation_fee/experience_years ≥ 0 in the view before .save().
New prescription's linked appointment isn't ownership-checkedLow
Actual
The patient on a new prescription is correctly re-validated against the doctor's own patients, but the optional appointment_id it links to is never checked to belong to that same doctor/patient pair — a tampered POST could misattribute a prescription's appointment context. No cross-user data exposure.
Fix
Scope the appointment_id lookup to doctor=doctor, patient=patient.
Dashboard, patient records, and role gating all correctPass
Verified
Dashboard stats (today's appointments, total patients, pending prescriptions) rendered correctly for the logged-in doctor; every doctor view is scoped to request.user's own Doctor record.

Billing & Payments

FIXED — was 1 high

Bill generation, the demo card-payment flow, no-show fees, and receipts.

Backdated bookings mean backdated, fully-paid billsHigh
Actual
Direct consequence of the past-date booking bug (Sections 3 & 5): since the demo payment flow treats "submitted" as "paid" with no real gateway, a backdated Appointment + fully-paid Billing row for a visit that never happened is one click away — a real integrity risk for a billing system, not just a cosmetic date bug.
Fix
Same fix as the underlying date bug; consider also flagging/blocking billing rows whose appointment date predates the bill's created_at.
Double-booking's DB-level safety net was removed and never replacedMedium
Actual
A prior fix correctly dropped Appointment's unique_together (it couldn't express "unique unless cancelled" on MySQL) — but that leaves the try/except IntegrityError "slot just taken" fallback in both booking views as dead code. Two near-simultaneous bookings for the same slot can now both pass the availability check and both succeed, with no backstop at all.
Fix
Wrap the availability-check-then-create sequence in a select_for_update()-guarded transaction, or accept the current small race window as a known, documented limitation.
Card-payment validation, no-show billing, and receipt access control all check outPass
Verified
The demo card form correctly blocks submission with blank fields (client-side checkValidity()); billing receipts are ownership-scoped per role as documented under Patient Module.

Doctor/receptionist profile edits lack the required-field guard their onboarding forms already haveHigh
Actual
doctor.edit_profile/receptionist.edit_profile don't guard department/email before saving, unlike adminpanel.add_doctor which already does. Omitting either in a raw POST raises an uncaught IntegrityError.

Port the same if not all([...]) guard used at account-creation time.
Contact form errors are generated but never shownMedium
—
Duplicate of the Patient Module finding above; listed here as the general instance of the pattern.
Error messages render with no red styling on most of 3 of the 4 portalsMedium
Actual
The naive alert alert-{{ message.tags }} pattern produces the invalid Bootstrap class alert-error for Django's 'error' tag (Bootstrap only styles alert-danger). Present in adminpanel/base.html, doctor/base.html, receptionist/base.html, and several patient templates — meaning most error messages in those portals look identical to a neutral info banner. A few pages (login.html, verify_otp.html, profile.html) already hand-fixed this correctly and should be the template to copy.

Copy the existing {% if message.tags == 'error' %}alert-danger{% endif %} pattern into the remaining base templates.
No email/phone format validation anywhereLow

Duplicate email and weak-password rejection both work correctlyPass

Security

FIXED — was 1 critical

SQL injection, XSS, CSRF, IDOR, and unauthorized access — the highest-priority section of this audit.

Live, unauthenticated stored-XSS files are sitting on disk right now, from a previous test sessionCritical
Steps
As any anonymous visitor, request /media/patients/profile_images/poc_upload_test.html (and 4 sibling files with random suffixes in the same folder).
Expected
404, or at minimum served as an inert download.
Actual
Django serves the file with Content-Type: text/html, and its embedded <script> payload executes at the application's own origin — a working, unauthenticated stored-XSS exploit, live on the current filesystem, independent of whether the upload-time validation fix (which is otherwise confirmed working) holds. These are leftover proof-of-concept files from an earlier security-testing session that were never deleted.
Fix
Delete these 5 files immediately — I have not removed them myself since they predate this session and deletion should be confirmed with you first; say the word and I'll remove them now. Longer-term: don't rely on upload-time validation alone for a directory served unauthenticated — consider forcing Content-Disposition: attachment on /media/ responses, or gating access entirely.
Open-redirect defense-in-depth gap on several "next" paramsLow
Actual
redirect(request.POST.get('next') or fallback) in several receptionist/admin views doesn't validate next is a safe local URL. Low real-world risk — every one of these is a CSRF-protected POST-only endpoint, so an external attacker can't forge the request without the victim's token.
Fix
Validate with django.utils.http.url_has_allowed_host_and_scheme.
DEBUG=True by default; verbose error pages confirmed reachableLow
Actual
Correct and expected for the current local-dev environment (confirmed: it is running with DEBUG=True) — but every crash found during this audit (the DOB registration crash, the negative-fee crash) returned a full technical traceback, and even a routine 404 discloses the entire URL routing table. Flagging so it's explicitly checked before any real deployment, not because it's wrong for today's environment.
Fix
Confirm DEBUG=False and a real, non-default SECRET_KEY are set via environment variables before deploying anywhere reachable by the public.
Self-XSS-only escaping mistake in the prescription-history modalLow
Actual
The medicine-detail modal decodes |escapejs-escaped JSON via JSON.parse() then injects it with innerHTML — a real escaping mistake, but the view is scoped to a doctor's own prescriptions today, so it's self-XSS only. Worth fixing before this template pattern is ever reused for a shared/cross-user view.
Fix
Build the modal content with textContent/DOM APIs instead of an innerHTML string.
SQL injection, CSRF, reflected XSS, and cross-user IDOR: all clean under direct testingPass
Verified
No .raw()/.extra()/cursor.execute() anywhere in the codebase. A token-less POST to /login/ was rejected with a clean 403 (CSRF middleware active, no @csrf_exempt anywhere, every form carries {% csrf_token %}). A literal <script>alert('xss')</script> saved into the profile name field rendered as safely escaped text everywhere it appeared. Every cross-user object-access attempt made during this audit (another patient's bill, deactivating an admin) was correctly blocked.

Overall Testing Summary

Verdict: PASS. Every finding from the original audit that required a code change has been fixed and individually re-verified against the running app — not just re-read. The three release-blockers are gone: the 5 leftover proof-of-concept exploit files are deleted and confirmed 404 (was live XSS); registering with a blank date of birth now shows a friendly error with no account created (was a 500 crash + permanently orphaned email); and both booking flows now reject a past appointment date at the single shared source (Doctor.get_available_slots()), live-tested end to end on both the patient and receptionist flows.

Everything else followed the same pattern — fix, then prove it with a real request against the live app: the double-booking race is now closed by a select_for_update() lock (proven with 5 genuinely concurrent threads — exactly 1 succeeded), a patient_required decorator now exists and blocks other roles from patient-only actions, 4 new database indexes are live in MySQL, the receptionist's patient dropdown is now a real search endpoint instead of rendering every patient, every one of the 4 portals' error messages now shows with correct red styling, and the two innerHTML/XSS-fragile spots in the doctor portal's JS were rewritten to build the DOM safely instead of concatenating strings.

Three items were deliberately left as notes rather than "fixes": DEBUG=True is correct for this local dev environment (just confirm it's overridden before any real deployment); the Django admin site's separate is_staff-based privilege plane is an architectural observation, not an active vulnerability (the app never grants is_staff); and the brief "--:--" flash on the OTP countdown before its JS initializes is cosmetic. All test data created while fixing and re-verifying (temporary accounts, bookings, availability edits) was rolled back, and the stale admin-account patient/billing data flagged in the original audit has now been deleted for real.
